# Phase 2C: proposed FLT/VIM verification and acceptance plan

2026-10-11. **Design only; no tests in this document have been implemented or executed.** All choices and numerical gates below are ASSUMED / PROPOSED until [L01–L13](phase2c_language_contract.md) are explicitly approved. Mathematical expectations are DERIVED from that proposed contract and the [reference-equation analysis](phase2c_vim_analysis.md).

The user has independently accepted the existing MVE/VD suite: 40/40 cases, MVE 32,078,912, VD 9,055,365, combined 41,134,277 parameters. Preserve all existing source, fixtures, tests, configuration behavior and N1. This plan adds tests in a separately scoped future language test area; it does not rewrite accepted tests. No classifier, adapter, dataset loader, objective or training loop is required for these checks.

## Execution and numerical contract

Reference and debug must use the full proposed architecture: 12 LE blocks, seven LD blocks, width 512, length 308, vocabulary 49,408, eight heads and FF width 2048. Small analytical fixtures test primitive mathematics only and cannot stand in for full-topology acceptance. FP32 CPU b=1 and b=2 complete forward/backward are mandatory; b=8 full-logit forward/backward is a separately reported capacity diagnostic. Available CUDA hardware adds b=1/2/8 diagnostics with a separately identified device result, not an unreported automatic skip.

Proposed fixed policies:

- CPU seed 0, four PyTorch threads, deterministic algorithms enabled; record Python/PyTorch/OS and BLAS/backend details. Fresh processes for memory cases and clean gradients for each isolation probe.
- FP32 comparisons use `atol=1e-6`, `rtol=1e-5`; FP64 analytical comparisons use `atol=1e-10`, `rtol=1e-8`. ID arrays, parameter identity, state reload equality, fixed-batch unaffected sample outputs and structural zero-gradient expectations use exact checks where specified below. All claimed nonzero gradients must be finite and have strictly positive norm in a deliberately noncanceling fixture.
- **N1 does not apply to any FLT/VIM test.** It remains only the existing MVE-T12 b=1-versus-b=2 check (`5e-6`, `1e-5`). If a new language test fails its proposed tolerance, record and investigate it; do not inherit N1, change the backend unnoticed or mark it xfail.
- No hidden skips, expected failures, width reductions, shortened sequences, omitted logits or silent dtype changes in a claimed full suite. Hardware-unavailable diagnostics are listed as **NOT RUN, hardware unavailable** outside the mandatory CPU suite. Capacity failures are explicit **FAILED/OOM** diagnostics, not successful tests. A claim of batch-8 capacity requires successful batch-8 execution on the named device.
- Probe objectives are deterministic scalar linear/quadratic functions of outputs. They are test instrumentation, not implementations of the paper's KL, CMC, language CE or other training losses. No optimizer or training epoch is necessary.

AD/trunk parameters, not a shared-encoder nonzero flag, are the decisive reconstruction-edge control. Select/construct a deterministic fixture with some nonzero residual entries and report coverage.

Report gradients to retained intermediate tensors as well as named parameter groups. A tensor supplied as independent detached memory is not evidence that production memory is detached; the production forward must pass FLT-T12/I02 separately.

## Parameter and resource reports

Later implementation evidence must include a machine-readable unique-parameter inventory and a human-readable table. Required totals: FLT 112,758,272; VIM subtotal 19,922,944 (already included); MVE 32,078,912; VD 9,055,365; visual+FLT 153,892,549. These exclude all future adapter/classifier/loss parameters. Count by parameter identity/storage and also inspect registered state names; do not count the tied vocabulary output twice. Report the zero-task-gradient Q/K subtotal without deleting it from the unique total.

Analytical memory expectations are in the [language contract](phase2c_language_contract.md). The full FP32 vocabulary allocation must have exactly 15,217,664 / 30,435,328 / 121,741,312 elements for b=1/2/8, or 58.051 / 116.102 / 464.406 MiB. Measure actual tensor `numel×element_size`; do not confuse MiB with decimal MB or report only parameter memory as runtime memory.

Each resource case must record:

- hardware/OS/backend versions, CPU threads or GPU name/total VRAM, dtype, seed, b/n/d/s and full versus feature-only route;
- warmup count and timed iteration count (proposed one warmup and three measured iterations), separate forward and forward+backward elapsed times; CUDA synchronization around timings;
- CPU process baseline, sampled peak RSS and available platform lifetime peak with sampling interval (short peaks may be missed); GPU current and peak allocated/reserved bytes after peak reset;
- actual output tensor bytes, parameter bytes and gradient bytes; whether autograd was enabled; no optimizer memory measurement claim without an optimizer, which remains outside scope;
- pass/failure/OOM/unsupported-device result and exact exception, never a substituted smaller batch reported as b=8.

Runtime has no invented speed threshold. Diagnose finiteness and full route execution first. Peak memory is measured on the named host; analytical inventories are not exact allocator forecasts. Repeated-call memory can legitimately retain allocator caches, so graph-leak acceptance should inspect live tensor/graph references and post-cleanup process trends rather than demand that reserved memory return to zero. Any proposed AMP/fused attention/checkpointing or vocabulary chunking is a separate change requiring numerical evidence and approval.

## Incremental order and final evidence package

After approval and tokenizer pinning, execute in this order:

1. Prompt/tokenizer and small FP64 VIM/attention/shifting/ownership tests. Confirm independent golden fixtures rather than generating expected values with the function under test.
2. Full-topology b=1 forward, parameter inventory, ordering and shape traces.
3. Full-topology b=1 backward and isolated gradient controls, including exact-zero Q/K expectations.
4. b=2 forward/backward, fixed-batch sample independence, memory-attention controls and visual integration.
5. Serialization/configuration consistency and the complete unchanged visual regression suite.
6. b=8 and available GPU resource diagnostics, with capacity limitations reported separately.
7. One complete mandatory CPU suite without skips/xfails/tolerance overrides; capture actual stdout/stderr, command, exit status and JUnit.

The later review package should contain approved contract versions, approval records, source/test files, immutable tokenizer provenance and fixtures, resolved language/visual configurations, parameter report, forward/backward tensor traces, per-parameter gradient summaries and detached-control comparisons, memory/runtime JSON, pytest/JUnit logs and a SHA-256 manifest. It must distinguish historical failures from final reruns and distinguish passed CPU tests from unexecuted GPU/batch-8 diagnostics. Do not retroactively alter older accepted artifacts.

Acceptance requires all approved mandatory IDs/cases, exact counts/sharing, preserved visual regression, analytical attention behavior, correct shifts/tie, isolated reconstruction gradient evidence and honest resource results. Architectural fidelity to an unavailable author implementation, reconstruction quality, classification accuracy and training convergence are not established by unit-test success.

Arithmetic budgets and local source review are complete; model execution, new pytest/JUnit logs, tokenizer golden arrays and actual FLT memory measurements are intentionally not produced before approval.
